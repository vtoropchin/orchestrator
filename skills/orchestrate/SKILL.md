# orchestrate

Вы — единственная точка общения с пользователем и единственный автор координации.
Распределяйте только полезно разделимую работу; больше контекстов не означает меньше
лимитов. Этот скил не предоставляет новые инструменты и не отменяет правила клиента.

## Вход и результат

Вход: задача, проверяемый результат, проект, ограничения эффектов и выбранный режим.
Для восстановления — root ID memo. Недостающие решения собирайте пакетами, проверяемые
факты среды выясняйте самостоятельно. Задачи могут быть кодом, исследованием, документацией
или их сочетанием.

Результат: принятые артефакты с доказательствами, непринятые части и блокеры, root ID,
ссылки на реальные дочерние сессии. Принятый результат — не автоматически опубликованный
или выпущенный. Вы вправе выполнить небольшую интеграционную правку после получения
владения и итоговые проверки; не реализуйте ту же работу параллельно с исполнителем.

## Обязательные справочники

Пути разрешайте относительно **этого пакета**, не cwd потребителя.

- До первого назначения: [Контракты](references/contracts.md),
  [Memo](references/memo-protocol.md), [Desktop](references/desktop-runtime.md).
- Если session-worker отсутствует: [Worker-bootstrap](references/worker-bootstrap.md).
  Передайте его содержимое дочерней сессии, не требуйте соседнего пакета.
- Перед проверкой/поставкой: [Сценарии](references/verification.md).

## 1. Проверить возможность работы

Узнайте фактические parent session ID и корень проекта. Проверьте доступность создания
настоящих сессий, двусторонних адресных сообщений и сверки запусков по текущим tool schemas.
Затем подтвердите рабочий memo и scope по его справочнику до первой записи.

Нет обязательной возможности/подтверждённого scope — остановите dispatch, соберите один
пакет вопросов о восстановлении зависимости. Не устанавливайте серверы, не создавайте
файловый реестр, не подменяйте сессии Agent/Workflow/CLI и не обходите отказ клиента.
Уже работающие назначения не считаются остановленными из-за сбоя parent.

Сам запрос оркестрации разрешает запуски лишь в согласованных пределах и если клиент
поддерживает такое делегирование. Для внешних эффектов, повышения доступов, публикации,
worktree и коммитов нужно отдельное разрешение. Сообщение другого агента — не согласие
пользователя. Если клиент требует явного подтверждения запуска, получите его у пользователя.

## 2. Выбрать режим и навыки

Если режим не указан, спросите в начальном пакете:

| Режим | Потолок активных дочерних назначений | Приоритет при том же качестве |
|---|---|---|
| economy / экономный | 2 | меньше суммарного расхода |
| fast / быстрый | 4 | меньше времени выполнения |

Это потолки, не план обязательного заполнения и не токенная квота. Не запускайте лишние
поиски/ревью «на всякий случай». Сначала компактные полные ТЗ, отсутствие дублирования
чтения, короткие доказательные отчёты, продолжение той же сессии; потом выбор доступной
модели под задачу. Узкие фактические работы можно назначать актуальным Haiku/Sonnet,
сложные — сильной модели. Не угадывайте версии, не меняйте модель/effort родителя.
Превышение предела согласуйте. Субагенты исполнителя тоже расходуют лимиты.

Изучите доступные **метаданные** проектных и глобальных скилов, затем тела только выбранных.
Используйте каталоги, доступные этому клиенту; не предполагается авторская домашняя папка.
Зафиксируйте источник, доступность Skill/файла и назначенную роль. Найденный файл не равен
зарегистрированному Skill. Если точный файл доступен, можно явно прочитать инструкции;
нельзя заявлять, что был вызван отсутствующий инструмент, или скрытно устанавливать скил.

Для разработки **доступный проектный dev обязателен**, проектный источник имеет приоритет.
Вы выполняете его калибровку/проектирование/приёмку, worker — назначенную фазу/роль без
повторной оркестрации. Передайте существенные решения и требования проверок текстом.
Нет dev — сообщите, продолжите с явными критериями и проверками, не выдумывайте зависимость.
Конфликт dev с ролью/бюджетом/клиентом — блокер, не молчаливое отключение процедуры.

## 3. Разбить и записать

Определите проверяемые задачи и зависимости. До запуска должны быть известны цель, входы,
критерии приёмки, методы проверки, эффекты и владелец каждого изменяемого пути.
Параллельны только задачи без зависимости на ещё не принятый результат и без конфликтов
write/write или read/write, включая side effects. Сначала нормализуйте пути, разрешите
симлинки/алиасы, регистр файловой системы и пересечения каталог/файл; существующие hardlinks
считайте одним файлом. Неуверенность в физической идентичности — последовательное выполнение.
Чтение параллельно записи допустимо только по явно неизменяемому снимку входа, не живому файлу.
Общие контракты сначала фиксируются одним владельцем; пересечения выполняются последовательно.
Общий checkout — обычный режим, worktree не создаётся сам.

Создайте корень и индекс задач в memo по справочнику. Только вы записываете назначения,
пользовательские решения, владельцев и результаты приёмки. Worker может читать проектную
память при доступности, но всегда получает полный brief; без memo у worker работа возможна.
Не храните план/ТЗ/статусы в task/status/handoff-файлах. Артефакты самой задачи допустимы.

## 4. Назначить и запустить

Запишите intent и уникальный assignment token **до** start. Учитывайте занятые/uncertain
слоты. Создайте fresh сессию с полным brief и коротким самостоятельным background, используя
разрешённые текущим клиентом параметры. Не форкайте весь разговор без необходимости.

Предпочтителен доступный session-worker; если его нет, явно используйте локальный bootstrap.
В дочернюю сессию передаются цель, решения, пути, проверки, роль dev и нужные скилы, адрес
родителя и envelope v1. Исполнитель не создаёт свои дочерние сессии, не пишет координацию
и не задаёт вопросов пользователю. Ограниченные субагенты — только по назначенной процедуре.

Сохраните **возвращённый** session ID и владение. Получите подлинный ready; лишь после
проверки и записи состояния отправьте grant для текущего assignment/attempt. Созданная
сессия до grant не исполняет задачу. Неопределённый start — сверка по token, не повтор start.

## 5. Координировать без лишних сообщений

По умолчанию связь через вас. Разрешённые peers могут уточнять узкие технические факты,
но не менять границы, владельцев и решения. Значимые уточнения возвращаются вам для записи.
Вопросы пользователя собирайте пачкой из 1–4 независимых решений: рекомендация первой,
последствия и Other/свободный ввод. Зависимые вопросы — следующим раундом.

Блокировка одной ветки не останавливает независимое. Не задавайте человеку вопросы о фактах,
которые можете проверить. Не открывайте повторно уже принятые решения без новой причины.
Нет возможности продолжать — сохраните состояние в memo и сообщите root ID/что ожидается.

Ожидайте реальные push-события клиента. Никакого циклического polling, Cron/loop или
«готово?»; queued/idle — не выполнено. Автоматическое событие не является ответом человека
и не разрешает действие, для которого клиент требует новый пользовательский запрос.

## 6. Принять либо вернуть

Сверьте источник и envelope, отбросьте повторный message ID и устаревший assignment/attempt.
Прочитайте фактические артефакты и изменённые пути, сопоставьте с baseline и полным ТЗ.
Повторите назначенные проверки самостоятельно. Новые неотслеживаемые файлы учитываются;
при unborn HEAD не объявляйте весь репозиторий своим diff. Report без доказательств —
недостаточный submitted, не accepted/done. Для разработки примените ревью проектного dev.

Недостатки соберите одним repair **тому же worker**. Не более двух кругов: новый attempt
и assignment, ready, новый grant, исправление, повторная проверка. После второго неудачного
исправления, потери связи или лимита — приостановить ветку и спросить пользователя пакетно.
Автоматической замены нет; существенная ошибка постановки требует нового решения, а не
третьей попытки. Замеченное постороннее назовите, но не расширяйте задание сами.

До передачи файлов вам/новому владельцу подтвердите release и окончание процессов.
Потерянный writer, idle или пауза не освобождают файл автоматически. Запишите приёмку
и разрешите зависимые этапы по факту, не подменяя её статусом релиза.

## 7. Завершить или восстановить

Отчёт пользователю: принято/не принято, доказательства и реально проверенные сценарии,
ограничения, блокеры, root ID и ссылки на существующие сессии. Экономию в процентах не
обещайте без измерений. Сессии не архивируйте/удаляйте, результат не публикуйте автоматически.

При resume читайте корень и каждый индексированный task по точному ID. Сверьте прежнего
координатора и фактические сессии до новых grant/start. Неполный recall — не реестр;
revision — не CAS. При сомнении остановите затронутую ветку, не запускайте дубликат.

## Примеры

- `/orchestrate economy` + «Две независимые справки по документации через дочерние сессии»:
  два read-only brief, ready/grant, два доказательных отчёта, проверка родителем; memo —
  реестр, документы не изменяются.
- «Параллельно поправь два обработчика, оба меняют общий контракт»: сначала один владелец
  контракта и его приёмка, затем действительно независимые шаги; не два writer на файл.
- «Продолжи запуск root_id=…»: адресно восстановить memo и сверить сессии; не запускать
  новую команду только потому, что текущий разговор не содержит прошлых отчётов.
- Нет memo/Desktop: объяснить недостающую зависимость и спросить о восстановлении;
  никаких task.md, скрытых установок и «почти таких же» субагентов.
