# Memo: реестр запуска и восстановление

Требуется настроенный пользователем MCP с операциями `memory_recall`, `memory_get`,
`memory_save`, `memory_update`; для снятия зависимости — поддержка `unlinks` в update.
Здесь описан существующий AgentMemory-контракт, не произвольный KV-store. Проверьте
фактически доступные схемы инструментов. Не выдумывайте дополнительные API, транзакции,
статус blocked, CAS, поля lease или возможность получить все записи одним recall.

## Проверка до первой записи

1. Найдите scope проекта из доступного проектного протокола/конфигурации MCP. Не считайте
   имя каталога доказательством. Не читайте секреты/.env и не настраивайте сервер.
2. Проверьте работающий сервис адресным чтением известной проектной записи: `memory_get`
   должен показать ожидаемый `scope`. Recall с явным scope может найти кандидата, после
   чего прочитайте его по ID. Пустой/семантически похожий результат не доказывает scope.
3. Сверьте чтение с проектным протоколом/конфигурацией. В новом проекте без известной
   записи получите явное подтверждение scope и подключения у пользователя до записи;
   не делайте пробную запись в сомнительное пространство.
4. Каждый save выполняйте с явным `scope: project:...`. Для update/get scope определяется
   адресуемой записью: сначала подтвердите ID и его scope. Не передавайте несуществующий
   параметр scope в инструменты, которые его не принимают.

Нет сервиса или подтверждения — **никакого dispatch и файлового fallback**. При сбое
записи во время работы приостановите новые grant/start, сообщите пользователю о состоянии,
сохраните владение текущих назначений до проверки. Не выдавайте неперсистентное изменение
плана за записанное. Worker без memo может работать по полному brief, но parent — нет.

## Записи и штатные поля

Корень создайте `memory_save(kind=task, type=epic, summary=..., status=todo, scope=...)`.
Сохраните возвращённый ID, передайте его пользователю как ключ восстановления.
Дочерние задания — `kind=task, type=task` с `part_of` на корень. В task обязателен summary.
Решения — атомарные semantic, существенные события — episodic; индексируйте нужные IDs
в корне/задаче. Не сохраняйте каждый токен, heartbeat и копию транскрипта.

Штатные статусы: `backlog`, `todo`, `doing`, `review`, `testing`, `release`, `done`.
При doing укажите фактическую ветку (пустую для не-Git) и `workflow: orchestrate`.
`review` — реальный PR, `release` — влито и ждёт релиза; accepted worker не означает
вливание/релиз. У исследования done возможен после фактической доставки принятого
результата; у разработки соблюдайте проектный цикл доставки. До неё приёмку отражайте
в content, не придумывая релиз. Пользовательский отказ не записывайте как разрешение.

Нативная блокировка — связь `blocked_by` **от заблокированной task к task-блокеру**,
не статус. Перед добавлением верните заблокированную задачу в todo, сохранив ход работы
в content. После разрешения блокера закройте его по факту либо снимите нужную связь через
`memory_update(unlinks=[{id: ..., rel: blocked_by}])` с записанной причиной. Для зависимости
между принятыми этапами снимайте связь после приёмки: не объявляйте код выпущенным ради
разблокировки. Все внутренние зависимости/acceptance также видны в содержимом задач.

## Content: компактный авторитетный индекс

Следующие поля — схема **содержимого**, не аргументы MCP:

```yaml
protocol: v1
run_id: <устойчивый ID, например root ID>
project: <проверенный корень проекта>
scope: <project:...>
parent_session_id: <фактический координатор>
mode: economy # fast
active_limit: 2 # 4 для fast
phase: planning # running | paused | accepted
revision: 0 # номер изменения, НЕ распределённая блокировка
task_ids: []
decision_ids: []
blocker_ids: []
```

Task content содержит полный brief, `assignment_id`, `attempt`, `repair_count`,
`session_id`, `launch_name`, `launch_token`, `launch_state` (`reserved|intent|bound|uncertain`),
пути и владельца, `ownership_released`, `acceptance` (`pending|rejected|accepted`),
краткий report/точную ссылку на его источник, обработанные message IDs текущего назначения.
При большом журнале храните только необходимые сообщения и индекс доказательств, не всё
содержимое сессий. Реальные артефакты результата могут быть файлами; файлы реестра — нет.

Только parent меняет координацию. Перед важным решением перечитайте актуальную task;
критические intent/bind/grant/ownership/acceptance записывайте и подтверждайте адресным
чтением до следующего внешнего эффекта. Корень не дублирует полные ТЗ дочерних задач.

## Последовательность запуска

1. Создать task в todo; записать её ID в корне. До успешной индексации task не исполняется.
2. Проверить зависимости, число занятых слотов, разрешённые эффекты и конфликты write/write
   и read/write на нормализованных физических путях, включая симлинки/hardlinks, регистр FS,
   каталог/файл и побочные записи. Неясный алиас/живое чтение во время записи — сериализация.
3. Сохранить attempt 0, assignment ID, уникальный token, намеченный короткий session handle
   и `launch_state: intent`. Token включить в brief/background запуска.
4. Вызвать разрешённый Desktop start один раз. Полученный ID записать в task:
   `launch_state: bound`, session ID и владелец. При неоднозначном исходе — uncertain.
5. Получить подлинный ready, сверить назначение и ограничения. Сохранить факт grant
   и doing с branch/workflow, затем отправить grant конкретному session ID.
6. Report сначала проверяется по источнику и текущему assignment/attempt/message ID,
   затем по артефактам, путям и независимым проверкам. Только parent пишет acceptance.
7. До передачи файлов подтвердить release и завершение процессов. Непринятый report
   может освободить владение, но не разрешает зависимый этап до приёмки результата.

Создание task до индексации может оставить orphan-запись, но не должно запустить worker.
Start между intent и bind может оставить **реальную сессию** без сохранённого ID: это не
основание повторять start. Grant при недоставленном сообщении не считается полученным:
родитель проверяет доставку/следующее событие, worker всё равно требует подлинный grant.

## Восстановление

Нужен root ID. Если он неизвестен, recall даёт только кандидатов: подтвердите нужный
запуск точным чтением, при неоднозначности спросите пользователя. Не создавайте новый
корень «вместо потерянного» для тех же файлов, пока прежний запуск не сверён.

Проверьте прежнего координатора через доступную информацию Desktop. Если он ещё управляет
запуском, не пишите общий реестр: нужна явная передача координации. Один revision/признак
idle не доказывает владение, отсутствие будущих событий или остановку процессов.
Нативных CAS/lease в этом протоколе нет, exactly-once гарантия не заявляется.

Прочитайте корень и каждый индексированный task через memory_get. Для intent/uncertain
однократно сопоставьте связанные Desktop-сессии/их контекст с launch token. Одна точная
найденная сессия — bind после проверки; неоднозначность/недоступный реестр — paused и
вопрос, не повторный запуск. Даже отсутствие в одном списке не доказывает, что start
не произошёл. Не подменяйте адресную сверку бесконечным опросом.

Если старый writer потерян, проверьте его остановку, фоновые процессы и оставшиеся правки
до нового владельца. Запрос на снятие/удаление сессии сам по себе не доказывает остановку.
После восстановления новый parent/assignment должен быть явно сообщён исполнителю по
проверяемому каналу; при невозможности подтвердить передачу работа остаётся приостановлена.
