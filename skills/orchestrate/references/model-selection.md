# Выбор модели child

Читайте перед каждым intent назначения, при repair/смене стратегии и при resume.
Цель — тратить лимиты сильных моделей только там, где от них зависит качество результата,
и не опускать качество кода ради экономии. Правила задают профили, а не имена моделей:
конкретные модели берутся из фактического списка клиента.

## Профили

| Профиль | Для чего | Типичная работа |
|---|---|---|
| `light` | Дешёвая быстрая модель | Поиск и извлечение фактов, инвентаризация файлов, сводка по точным источникам, механические правки по готовому списку, проверка детерминированного вывода команд |
| `coding` | Сильная модель для кода | Написание и правка кода и тестов, локальный dev-цикл T0–T1, ревью кода, проектная настройка (`adapt`) |
| `top` | Самая сильная доступная модель | Проектирование, неясные требования, T2–T3, высокий риск и пути безопасности, разбор причин после неудачных repair |

Профили упорядочены: `light` < `coding` < `top`. «Не ниже X» значит X или старше.

## Пороги качества (не нарушаются ради экономии)

1. **Код пишет и принимает не ниже `coding`.** Любое назначение, которое меняет код, тесты,
   сборку или конфигурацию исполнения, и любой verifier такого результата.
2. **Verifier не слабее автора.** Профиль verifier ≥ профиля автора и ≥ порога результата.
3. **Высокий риск — `top`.** Пути security/high из `REVIEW.md`, миграции данных, публичные
   контракты, Git-delivery с чужим baseline: автор-lead и verifier на `top`. Риск поднимает
   тех, кто пишет (код, документы, данные, внешние эффекты), решает или принимает. Read-only
   сбор фактов (scout, worker без какой-либо записи) риск задачи не поднимает — по правилу 6
   он ничего не решает.
4. **Неизвестное считается старшим — для пишущих и решающих.** Размер или риск неизвестен —
   сначала scout на `light` собирает факты, затем оценка по ним. Пришлось назначать без
   фактов — профиль как для T2 и высокого риска. Сами вы код для оценки не читаете.
5. **Понижения нет.** Repair, resume и замена actor не понижают уже выбранный профиль.
6. **Дешёвая модель не принимает решений.** `light` возвращает факты со ссылками; выводы,
   критерии, границы и приёмку делает назначение не ниже `coding` или parent.

## Выбор по роли

Сначала оцените размер (T0–T3 по определению `dev`, если он доступен; иначе: T0 — опечатка
или константа, T1 — локальная правка, T2 — новая функция или несколько модулей, T3 — новая
система или сквозное изменение) и риск по путям `REVIEW.md`. Затем:

| Роль | Условие | Профиль |
|---|---|---|
| Scout | Сбор фактов со ссылками, inventory, поиск по точным вопросам — при любом размере и риске задачи | `light` |
| Planner | Границы, критерии, ТЗ, декомпозиция, выбор вариантов — по фактам scout | `top` для T2–T3 или высокого риска, иначе `coding` |
| Dev-lead | T0–T1 и риск не высокий | `coding` |
| | T2–T3, высокий риск или неизвестно | `top` |
| Worker | Только чтение, документация по готовому плану, механика по точному списку | `light`; с записью (документы, данные, внешние эффекты) на высоком риске — `top` |
| | Пишет код/тесты/конфиги или выполняет `adapt` | `coding`; высокий риск — `top` |
| Integrator | Слияние веток и текстовые конфликты | `coding`; высокий риск или много смысловых пересечений — `top` |
| Verifier | Результат с кодом | max(`coding`, профиль автора); высокий риск — `top` |
| | Read-only или документ | не ниже профиля автора |
| | `final_git` | не ниже профиля content-verifier этой поставки; в `worktree-integration/v1` — не ниже самого сильного автора запуска |

Dev-lead на `top` сам решает по `dev`, делегировать ли код `implementer` на модели для кода;
dev-lead на `coding` ведёт цикл сам. В `bounded_subagents` lead-а можно указать потолок
профиля пула; потолок не ниже порогов выше.

**Jev.** Если `runtime.jev.mode` не `off`, перед выбором профиля вызовите калибровку Jev
([jev](jev.md)): в `shadow` она записывается рядом с вашей оценкой, в `apply` её профиль
применяется (поднять можно, понизить нельзя). Пороги выше действуют в любом режиме.

Оценку parent и выбранный профиль запишите в brief (`context`) одной строкой:
«оценка parent: T1, риск low; профиль coding». Если калибровка child выше оценки и требует
старшего профиля, child до содержательной работы возвращает `question` с фактами калибровки.
Parent запускает новое назначение на нужном профиле; работа на младшем не продолжается.

## Эскалация вместо дорогого старта

Начинайте с самого дешёвого профиля, который проходит пороги, и поднимайте по фактам:

- `light`-назначение не прошло проверку или вернуло неполные факты — новая стратегия
  на следующем профиле; repair на `light` не повторяйте.
- Два неудачных repair стратегии на `coding`, и причина — качество рассуждения (неверная
  модель предметной области, повторяющиеся ошибки логики), а не brief, среда или права, —
  новая стратегия на `top`. Причину и смену профиля сохраните в history refs стратегии.
- Блокер среды, доступа или нехватки данных эскалацией модели не лечится.
- При `runtime.jev.mode` не `off` причину неудачи перед эскалацией классифицирует
  `jev.py repair-cause` ([jev](jev.md)); `parent_decides` — решаете по правилам выше.

Смена модели — это новый запуск: действуют правила замены actor (stop/release, новые
назначение, version, detail IDs, ready/grant). Модель уже запущенного child не меняется.

## Каталог моделей клиента

Профили — классы качества, а не три конкретные модели: моделей у клиента может быть
сколько угодно, у разных провайдеров. Каталог собирается один раз на клиента и список
моделей и хранится в `runtime.model_catalog` control (при resume — переиспользуется):

```yaml
model_catalog:
  client: <клиент>
  source: <схема инструмента запуска / документация клиента>
  collected_at: <дата>
  models:
    - id: <ID или алиас, который принимает схема запуска>
      profile: light | coding | top   # класс качества; назначает parent
      cost_rank: 1                    # 1 — самая дешёвая; null — неизвестно
      context_tokens: <число | null>
      evidence: <откуда класс и цена: ссылка, цитата описания>
```

1. Получите фактический список моделей, которые клиент позволяет выбрать для child
   (схема инструмента запуска, документация клиента). ID по памяти не угадывайте.
2. Каждой модели назначьте `profile` по её описанию у клиента/провайдера: `top` — самые
   сильные в рассуждении и проектировании, `coding` — сильные для кода, `light` — дешёвые
   быстрые. Не уверены — старший класс. Одна модель — один класс; одинаковые классы у
   разных моделей допустимы.
3. `cost_rank` — по цене или расходу лимита у клиента (1 — дешевле всех); одинаковая цена —
   одинаковый ранг. Неизвестная цена (`null`) считается самой дорогой в своём классе.
4. **Выбор для назначения:** кандидаты — модели с `profile` не ниже порога назначения и
   достаточным контекстом; берётся минимальный `cost_rank`, при равенстве — младший
   профиль, затем порядок каталога. Так дешёвая сильная модель выигрывает у дорогой
   модели того же или младшего класса.
5. Кандидатов нет — `blocked: model_below_floor` для этого назначения, без тихого понижения.
   Модели без выбора по ID у клиента нет — шаг 6.
6. Клиент не даёт выбрать модель child — child наследует модель клиента; запишите
   `selection: unsupported`. Это не блокер, но и экономии моделью нет.
7. Effort/уровень рассуждения, если клиент его задаёт per-child: `light` — низкий,
   `coding` — высокий для кода и ревью, средний иначе; `top` — по умолчанию клиента.
   Порог тот же: effort не понижает назначение ниже порога качества.

## Модель самого parent

Parent работает на модели, которую пользователь выбрал при старте сессии, и сам её не меняет.
Рекомендуемая — самая сильная в каталоге (`top`): parent декомпозирует работу, пишет brief
и принимает результат, а ошибка здесь стоит переделки у всех child. Контекст parent мал
(цель, решения, квитанции), поэтому сильная модель здесь дешевле, чем у пишущих child,
которым этот файл подбирает самую дешёвую подходящую модель.

Если модель parent известна и по каталогу ниже `top`, а работа T2–T3 или высокого риска,
одной строкой сообщите пользователю: рекомендуется перезапустить сессию на старшей модели
(назовите её из каталога). Это не блокер: продолжайте, если пользователь не решил иначе.
Модель parent неизвестна — ничего не сообщайте. Child всё равно получают профиль по таблицам
выше, независимо от модели parent.

Модель, effort и права parent не меняйте. Явное решение пользователя о модели старше
таблицы; если оно ниже порога, одной строкой сообщите риск и выполняйте решение.

Запишите каталог в `runtime.model_catalog` control, а выбор — в control назначения:

```yaml
model:
  profile: coding # light | coding | top
  model_id: <фактический ID/алиас клиента либо inherit>
  effort: <значение клиента либо null>
  reason: <оценка T/риск, роль, правило; эскалация — ref причины>
  cost_rank: <из каталога | null>
  selection: chosen # inherited | unsupported | user_decision
```

## Ориентиры по клиентам

Подсказка, не гарантия: списки моделей меняются быстрее скила, сверяйте с клиентом.

| Клиент | Обычные классы в каталоге |
|---|---|
| Claude Code (CLI, IDE, web, Desktop) | `top` — новейшее семейство верхнего класса из доступных (Fable/Mythos); `coding` — новейший Opus; `light` — Haiku, для сводок с рассуждением — Sonnet. Алиасы (`opus`, `sonnet`, `haiku`) берите, только если их принимает фактическая схема запуска |
| DeepSeek Harness, Hermes Agent, другие | По списку моделей профиля/провайдера; нет выбора per-child — `selection: unsupported` |

## Отчёт

В итоге работы перечислите профиль и модель каждого запуска и эскалации с причиной;
при Jev — строки из раздела «Отчёт» [jev](jev.md).
Экономию называйте только по замерам клиента (токены, лимиты), не по ожиданию.
