# Адаптер v3: Codex CLI (`transport: session`)

Читайте этот файл, только если текущий клиент — Codex CLI с инструментами совместной
работы агентов. Общая модель возможностей — в [runtime.md](runtime.md). Имена ниже
наблюдались в Codex CLI 0.167–0.169 (`multi_agent_v2`); клиент меняется быстрее скила,
поэтому сверяйте фактические схемы инструментов в текущей сессии.

## Возможности

| Возможность | Инструмент | Что подтвердить |
|---|---|---|
| SPAWN | `spawn_agent` | Поле `fork_turns`: значения `"all"` и `"none"`, **умолчание `"all"`** — наследует беседу parent |
| CHANNEL | `followup_task` (target, message) — новый ход child; `send_message` — доставка сообщения | Реальный адрес child, статус доставки |
| WAKE | `wait_agent` с тайм-аутом | Возврат по событию child; тайм-аут — не событие |
| RECONCILE | `list_agents`, метаданные child-сессии | Фактические IDs и состояния своих child |

## Запуск

- Передавайте `fork_turns: "none"` **в каждом** `spawn_agent`: scout, writer, integrator,
  repair на новой стратегии, verifier. Опущенное поле означает `"all"`.
- Машинная проверка: в метаданных child с наследованием есть `forked_from_id` parent.
  Нашли его у verifier — grant не выдавайте, запустите нового. Сохраните в control
  `runtime.mapping.spawn_context: fork_turns=none`.
- `fork_turns` действует только при создании. `followup_task` продолжает child с его
  накопленным контекстом, поэтому им передавайте только grant, ответ на question и repair
  того же назначения, и только если модель и усилие child соответствуют решению в control.
  Модель и усилие задаются при запуске, поэтому иначе — новый `spawn_agent` по правилам
  замены actor. Новая задача — новый `spawn_agent`.
- `"none"` убирает беседу, но не инструкции клиента: `AGENTS.md`, каталог скилов, MCP и
  права sandbox задаёт клиент. Доступность memo у child проверяйте отдельно (MCP может
  отсутствовать, например при запуске с игнорированием пользовательского конфига).

## Ожидание

Каждый `wait_agent` — полный запрос parent. Ждите всех активных child одним вызовом с
наибольшим допустимым тайм-аутом; после тайм-аута снова ждите, без `list_agents`.
`list_agents` — только при uncertain (неясный запуск, потерянный ответ).

## Git в sandbox

Режим `workspace-write` защищает `.git` и разыменованный git-dir связанного worktree:
`git add`/`git commit` из worktree child может упереться в запрет записи `index.lock`.
До обещания самостоятельного коммита проверьте предпосылку из [runtime.md](runtime.md)
(право записи в фактические `git-dir`/`git-common-dir` либо рабочий путь одобрения
локальных Git-команд, например через auto-review). При `approval_policy = never` без такого
права коммит недоступен: сообщите пользователю, какое разрешение нужно, или используйте
запасную линейную policy.

Прогноз для `approvals.expected` ([runtime.md](runtime.md)), наблюдался в 0.167: в
`workspace-write` одобрения требуют `git add`/`commit`/`merge` из связанного worktree (запись
в git-dir вне workspace) и тесты или сборки, которые пишут вне writable roots (кэши в домашнем
каталоге, временные каталоги) или ходят в сеть. Тесты, поданные с повышением прав
(`sandbox_permissions: "require_escalated"`), получают решения auto-review не на каждую
команду: в одном запуске 12 команд `go test` дали 5 решений, причину журнал не называл.
Прогнозируйте группу тестов, а не число решений. Удаление (`rm -rf` своих временных
каталогов) проверялось auto-review даже внутри writable roots и без повышения прав —
вносите его в `expected`. Если одобрения проверяет auto-review, каждая
проверка — отдельная модельная сессия со своим расходом: в одном наблюдавшемся запуске пять
таких сессий дали 44 запроса и ≈410 тыс. входа без кэша, все решения allow, из них 21 запрос
пришёлся на интегратора. Политику ради экономии не меняйте; делайте расход видимым.

## Расход

Журнал сессии — JSONL. События расхода: `type: "event_msg"`, `payload.type: "token_count"`,
накопленные значения в `payload.info.total_token_usage` (`input_tokens` включает
`cached_input_tokens`; есть `output_tokens`, `reasoning_output_tokens`). Запрос — событие,
где `total_tokens` вырос; сверяйте их число с уникальными ответами модели в том же журнале.

Сессии auto-review пишут свои журналы (`session_meta.payload.source.subagent.other:
"guardian"`). В 0.167.0-alpha.3.2 связь — `session_meta.payload.parent_thread_id`: он равен
`session_meta.payload.id` агента, запросившего одобрение; дальше ID агента связывается с
назначением по control. `session_id` указывает на общую корневую сессию, а `cwd` может быть
корнем проекта — для привязки они не годятся, время и cwd — только сверка. Нет поля в
текущей версии — привязка по окну времени назначения с пометкой «приближение».

Доставки и пробуждения считайте отдельно. Служебный финал child приходит в журнал parent
как `type: "response_item"`, `payload.type: "agent_message"` с автором child и заголовком
`Message Type: FINAL_ANSWER`; если перед ним `inter_agent_communication_metadata` с
`trigger_turn: false`, это доставка без пробуждения. Пробуждение — возврат `wait_agent` по
событию или новый ход parent.
