# Подключение набора к проекту и клиентам агента

Файлы скилов в проект кладёт установщик (`make install PROJECT=…` в репозитории скилов или
стандартный skills CLI). `adapt` их не копирует и не правит: он подключает уже установленный
набор к клиентам агента и проекту. Этот справочник — что создаётся, что сливается и что не
трогается никогда.

## 1. Где установлен набор

- **Каталог скилов** — родительский каталог этого скила (`adapt`). Соседние каталоги — скилы
  набора: `dev`, `clean-architecture`, `solid-design`, `component-structure`,
  `architectural-boundaries`, `use-cases-and-entities`, `testable-architecture`,
  `code-organization`, `details-and-deferral`, `memo`, `memo-bootstrap`.
- Установщик мог положить скилы в общий каталог (обычно `.agents/skills/`) и симлинками —
  в каталоги отдельных клиентов (`.claude/skills/` и др.). Определить фактический путь
  (`pwd -P`) и пути-симлинки: физический путь становится `<dev>` в `REVIEW.md`, а по
  симлинкам определяются клиенты (§2).
- Нет скила `dev` рядом — набор установлен не целиком: назвать недостающие скилы и предложить
  повторить установку, а не копировать файлы самому.
- Установка глобальная (каталог вне репозитория) — работать можно, но `<dev>/**` в `REVIEW.md`
  не пишется, а в отчёте — строка, что инструменты ревью лежат вне репозитория.

## 2. Клиенты проекта

Клиенты определяются по каталогам, куда установлены скилы, и по уже существующим файлам
(`.claude/`, `CLAUDE.md`, `AGENTS.md`, конфиги MCP); итог подтверждается у пользователя
в плане (фаза 2).

| Каталог скилов | Клиент |
|---|---|
| `.claude/skills/` | Claude Code |
| `.hermes/skills/` | Hermes Agent |
| `.agents/skills/` | общий каталог: его читают DeepSeek Harness, Codex и другие клиенты `AGENTS.md`; какие из них реально используются — спросить |
| другой | клиент по документации установщика; не удалось определить — спросить |

Для каждого клиента решается:

| Что | Как |
|---|---|
| Файл правил | `rules-file.md` |
| Именованные агенты | клиент поддерживает определения агентов в проекте и для него есть адаптер — создать из файлов ролей скила `dev` (`references/agents/*.md`); адаптера нет — не создавать: `dev` запускает роли общим субагентом |
| Память `memo` | §4 |

Адаптеры клиентов: [runtime-claude-code.md](runtime-claude-code.md). Для клиента без адаптера
формат агентов и подключения MCP берётся из его документации и проверяется на месте; не
подтвердилось — шаг пропускается и попадает в отчёт.

## 3. Состав записей

| Путь в проекте | Действие | Примечание |
|---|---|---|
| Каталоги скилов набора | **не трогать** | обновляет только установщик |
| Определения агентов клиента | создать; при обновлении — §5 | только для клиентов с адаптером |
| Файл правил (`AGENTS.md`/`CLAUDE.md`) | дополнить блоком «Архитектура» | `rules-file.md`; чужие разделы не трогать |
| `REVIEW.md` | нет файла — каркас; есть — только дописать недостающее | `review-template.md`; **никогда не перезаписывать** |
| `.gitattributes` | дописать `REVIEW.md merge=union`, если нет | не перезаписывать |
| `agentmemory.toml` | из `assets/agentmemory.toml` с подставленным именем | только если подключается `memo` и файла нет |
| `.env` | создать с пустым `DEEPSEEK_API_KEY=`, если нет | только если подключается `memo`; ключ вписывает пользователь |
| `.gitignore` | дописать `.env`, если нет | только если подключается `memo`; не перезаписывать |
| Конфиги MCP и хуков клиентов | **слияние**, §4 | только сервер и хуки `memo`; чужие ключи не трогать |
| Средство принуждения правила зависимостей | создать по согласию (фаза 6) | `enforcement.md` |

## 4. Память `memo`

`memo` — внешний инструмент пользователя; набор его не устанавливает.

1. `command -v memo`. Не найден → память не подключается: не создавать `agentmemory.toml`,
   `.env`, строку в `.gitignore`, конфиги MCP и хуки; в отчёт — строка «набор работает без долговременной памяти, `dev`
   проговаривает решения в отчёте». Скилы `memo` и `memo-bootstrap` остаются установленными:
   без сервера они сообщают об этом и не мешают.
2. Найден → **имя проекта в памяти**: по умолчанию имя каталога проекта, подтвердить у
   пользователя — оно навсегда становится scope в общей базе. Подставить в `[scope] project`
   `agentmemory.toml`. Скилы `memo`/`memo-bootstrap` читают имя оттуда и не правятся.
3. **Подключение к клиентам.** Если у `memo` есть своя команда настройки клиента (например,
   `memo init`), предпочесть её: она знает форматы клиентов. Иначе — шаблон адаптера клиента
   (`runtime-claude-code.md`) или документация клиента по подключению MCP-сервера stdio:
   команда `memo`, аргументы `-config <корень проекта>/agentmemory.toml`. В конфиги
   подставляется фактический путь из `command -v memo`, никогда — чужой абсолютный путь.
4. Слияние конфига: прочитать существующий, добавить только сервер/хуки `memo`, не заменяя
   чужие элементы; уже есть `memo` с другими параметрами — показать расхождение и спросить.
   После записи перечитать и проверить валидность (JSON/YAML/TOML).
5. Частичная деградация (бинарь есть, ключа reasoner нет) допустима: recall работает без
   суммаризации. Это строка в отчёте, а не повод отказаться.

## 5. Обновление набора

Обновление — это новая установка тем же установщиком и повторный `adapt` в режиме обновления.

1. **До установки** — рабочее дерево чистое или изменения закоммичены: так видно, что
   установщик заменил.
2. **Проектные дополнения в файлах скилов.** Правило набора: проектное живёт в файле правил и
   `REVIEW.md`, а не в скилах. После установки посмотреть `git diff -- <каталог скилов>`:
   строки, которые проект дописывал в скилы и которые новая версия убрала, — показать
   пользователю и перенести в файл правил (или `REVIEW.md`), а не возвращать в скил.
   Если пользователь настаивает на правке скила — трёхстороннее слияние
   `git merge-file -p <версия проекта> <прежняя версия набора> <новая версия>`: прежняя и новая
   версии берутся из истории репозитория скилов (`git log -- skills/<скил>/<файл>`),
   конфликт решает пользователь.
3. **Определения агентов** создаются заново из новых файлов ролей. Файл агента в проекте
   отличается от того, что `adapt` создал бы из **прежней** версии роли, — его правил проект:
   показать `diff` и спросить, а не затирать.
4. **Не трогать**: файл правил (кроме недостающих пунктов блока), `agentmemory.toml`, `.env`,
   конфиги MCP/хуков, если `memo` уже подключён. `REVIEW.md` — только дописать недостающее
   (`review-template.md`, «Обновление набора»).

## 6. Проверки после записи

1. Конфиги валидны и содержат прежние ключи проекта.
2. `REVIEW.md` содержит все разделы шаблона; при обновлении `git diff REVIEW.md` показывает
   только дописанное; `review-lint` зелёный или его нарушения исправлены в этой же задаче.
3. `.env` в `.gitignore`; ни одного секрета в записанных файлах.
4. Скилы и агенты видны клиентам: многие клиенты читают их при старте сессии — назвать
   перезапуск сессии ручным шагом.
