# Источники расхода

Читайте, когда для разбора нужны числа запросов и токенов. Расход показывает клиент;
у части клиентов его нет вовсе — тогда выводы о стоимости не делаются.

## Общие правила подсчёта

- **Запрос к модели** — уникальный ответ модели с записанным расходом. Число вызовов
  инструментов его не заменяет: один ответ может содержать и текст, и вызов.
- **Накопленные счётчики** считайте разницей: от первого события сессии (или от момента
  выдачи назначения), а не абсолютным значением. Child, созданный fork'ом, может начинать
  журнал с копии счётчиков parent — проверьте первое событие.
- Разделяйте вход из кэша, вход без кэша и output (reasoning — отдельно, если клиент его
  выделяет). Сравнивать только суммы — недостаточно: кэшированный вход дешевле.
- Расход child считайте по каждой child-сессии и, если можно, по назначениям внутри неё.
  Вход первого запроса child — оценка размера унаследованной истории плюс бриф и инструкции.
- Отдельный расход независимых проверяющих держите отдельной строкой.

## Codex CLI

Журнал сессии — JSONL. События расхода: `type: "event_msg"`, `payload.type: "token_count"`,
накопленные значения в `payload.info.total_token_usage` (`input_tokens` включает
`cached_input_tokens`; есть `output_tokens`, `reasoning_output_tokens`). Учитывайте
только события, где `total_tokens` вырос. Метаданные child-сессии, созданной с наследованием
истории, содержат ссылку на родительскую сессию (`forked_from_id`) — это машинная проверка
наследования, надёжнее наблюдения самого child.

## Другие клиенты

Ищите в документации клиента экспорт журнала или трассы модельных запросов. Нет — в
разборе указывайте «расход недоступен» и опирайтесь на счётчики событий протокола.
