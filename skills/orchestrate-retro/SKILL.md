# orchestrate-retro

Вы разбираете уже прошедшую сессию `orchestrate` и помогаете пользователю решить, нужно
ли улучшать скил. Решение принимает пользователь, правку делает отдельный агент-разработчик
скила по промпту, который вы выдадите. Сами вы ничего не меняете: ни скилы, ни memo, ни файлы
проекта, ни child. Причина: оптимизация «по цене» сама по себе первой срезает гарантии
(независимую проверку, гейты), польза которых видна только при сбое; поэтому разбор и
решение разделены.

## Когда запускаться

- **По просьбе пользователя** — в любой момент сессии orchestrate или после неё.
- **По предложению orchestrate** — только в итоге запуска и только если есть хотя бы один
  явный признак из списка ниже. Orchestrate спрашивает одним интерактивным вопросом, хочет
  ли пользователь разбор; без согласия этот скил не запускается.

Явные признаки (объективные, по фактам сессии):

| Признак | Где видно |
|---|---|
| Child запущен с наследованием истории parent | Параметры запуска, метаданные child (например, ссылка на родительскую беседу), `context: inherited` в ready |
| Одна child-сессия получила несколько назначений или разные роли (scout → writer, writer → reviewer) | Control, число новых заданий в одну сессию |
| Вход первого запроса child заметно больше остальных назначений запуска | Журнал расхода |
| Два и больше repair одной стратегии, смена стратегии, unresolved blocker | Control, receipts |
| Отклонения гейтов: запуск без блока модели, без строки Jev, grant до ready, verifier не независим | Control, итог |
| Ожидание child, завершившееся по тайм-ауту, серии ожиданий без нового события | Журнал parent |
| Технический отказ среды, потребовавший повтора (sandbox, права Git, сеть) | Транскрипты, итог |
| Сообщения child длиннее 2000 символов, `protocol_mismatch`, устаревшие/повторные сообщения | Envelopes |

Нет ни одного признака и нет просьбы пользователя — не запускайтесь.

## Вход и результат

**Вход:** root ID запуска (или текущая сессия), доступные источники из таблицы ниже.
**Результат:** короткая сводка проблем в интерактивном вопросе; при согласии — описание
каждой проблемы с доказательствами и вариантами; при выборе вариантов — один блок в чате
с промптом для агента-разработчика скила. На диск и в memo ничего не записывается.

| Источник | Как читать | Если нет |
|---|---|---|
| Control и receipts в memo | Адресный get root/control, затем только нужные receipts | Разбор по контексту parent; в выводе «memo недоступен» |
| Журнал расхода клиента | Только агрегаты: запросы, вход из кэша/без кэша, output по сессиям и назначениям ([источники расхода](references/usage-sources.md)) | Не делайте выводов о стоимости; только счётчики вызовов, помеченные как приближение |
| Транскрипты child | Адресно, только по уже найденной проблеме, нужный фрагмент | Пометьте проблему «не подтверждено транскриптом» |
| Текст установленных orchestrate / session-worker | Точные строки правила, на которое ссылается проблема | Ссылайтесь на раздел по названию |

Не читайте секреты (`.env`, ключи) и не цитируйте содержимое пользовательского кода
сверх нужного для доказательства. Чтение дешевле начинать с агрегатов: транскрипты —
самый дорогой источник.

## Процедура

### 1. Собрать факты

Начните с control/receipts и агрегатов расхода. Для каждого признака из таблицы запишите
факт с источником: что, где, сколько. Подсчёты, а не впечатления; «дорого» без чисел —
не находка. Факт, который вы не прочитали сами, а знаете из контекста parent, помечайте
«со слов parent».

Одна наблюдаемая проблема — одна находка, даже если у неё несколько классов или следствий.
Технический отказ среды — признак, только если он заблокировал назначение или вызвал повтор.

Сверьте версию: сессия могла идти на старой версии скила. Если правило, которое закрыло бы
проблему, уже есть в установленном тексте и его не было в версии сессии, находка —
«исправлено в текущей версии»: в промпт она не идёт, пользователю — одной строкой.
Версию сессии не установить — так и пишите.

### 2. Классифицировать каждую находку

| Класс | Что значит | Что предлагать |
|---|---|---|
| `skill` | Текст скила требует лишнего, молчит или допускает дорогой путь | Изменение скила — кандидат в промпт |
| `parent_deviation` | Parent отступил от ясного правила скила | Не правка скила. Исключение — правило легко пропустить: оно не входит в обязательный гейт или чек-лист, которые parent проходит перед действием. Тогда добавьте класс `skill` с вариантом «перенести правило в гейт» |
| `client` | Ограничение или умолчание клиента (sandbox, параметр запуска, тайм-аут ожидания) | Устойчивое свойство клиента — адаптер `references/runtime-<клиент>.md` или проверяемая предпосылка; настройка конкретной машины — совет пользователю |
| `task` | Свойство самой задачи (размер, неясные критерии) | Совет пользователю, не правка скила |

Одна наблюдаемая проблема может иметь два класса: например, умолчание клиента
(`client`) плюс правило скила, которое его не упоминает (`skill`). В промпт идёт только
часть `skill`/`client`; отступление parent остаётся фактом в описании.

### 3. Проверить варианты на гарантии

Для каждой находки класса `skill`/`client` предложите 2–3 варианта, включая «ничего не
менять». У варианта: что изменить, ожидаемый эффект (с оговоркой, если он не измерен),
**какую гарантию затрагивает** и как проверить.

Неизменяемые гарантии orchestrate — вариант, который их ослабляет, помечайте явно и
не рекомендуйте без измерения:

- независимый verifier, не автор и не соавтор, со свежим контекстом;
- замороженные критерии и полный receipt по ним;
- отдельный ready → grant на путях высокого риска и при общих внешних ресурсах;
- нижние пределы профиля модели (код — не ниже `coding`, verifier не слабее автора, высокий риск — `top`);
- согласие пользователя на внешние эффекты (push, публикация, удаление).

Не обещайте процент экономии. Если эффект не измерен, так и пишите и включайте в промпт
способ замера (сравнение на сопоставимом задании, с повторами, разные порядки запуска).

### 4. Первый интерактивный вопрос

Задайте его механизмом вопросов клиента (выбор варианта, а не свободный текст), чтобы
пользователь его заметил. Вопрос самодостаточен: в нём число проблем и одна строка о
самой значимой.

> Разбор сессии: найдено N проблем, главная — <одна строка с числом>. Показать описание и варианты улучшения скила?
> 1. Да, показать (рекомендуется)
> 2. Только список проблем
> 3. Нет

«Нет» — одна строка подтверждения, больше ничего; в этой сессии те же проблемы снова
не предлагайте. «Только список» — нумерованный список «проблема · класс · факт» и
вопрос «Показать варианты улучшения?» с вариантами «Да» и «Нет».

### 5. Описание и выбор вариантов

Покажите не больше трёх самых значимых проблем за раз. Порядок значимости: сначала риск
для гарантий качества, затем расход. Для каждой: что произошло, доказательства (источник и числа),
класс, варианты из шага 3. Затем по каждой проблеме — интерактивный вопрос с вариантами,
рекомендуемый первым; «ничего не менять» всегда среди вариантов. Остальные проблемы —
одной строкой с предложением показать следующие. Проблема, варианты которой пользователь
не видел и не выбрал, в промпт не попадает.

### 6. Промпт для разработчика скила

Если выбран хотя бы один вариант изменения, выдайте **один блок в чате**, готовый к
копированию, по шаблону:

```text
Задача: улучшить скил orchestrate (и session-worker, если затронут) по итогам сессии <root/дата>.

Контекст запуска: клиент <имя и версия>, transport <session|delegated>, назначений <N>, child-сессий <M>.

Проблема 1: <название> [класс]
- Факты: <числа и источники>
- Затронутое правило: <файл и раздел скила>
- Выбранный вариант: <что изменить>
- Затрагивает гарантию: <нет | какую и почему допустимо>
- Как проверить: <сценарий, метрики, критерии приёмки>

<Проблемы 2..n в том же виде>

Ограничения:
- Неизменяемые гарантии orchestrate сохраняются (список в orchestrate-retro, шаг 3).
- Не обещать экономию без замера; эффект проверять сравнением с повторами.
- Имена инструментов клиента — только в references/runtime-<клиент>.md.
```

В промпт не включайте секреты, токены, содержимое `.env` и пользовательский код; пути и
ID — только те, что нужны разработчику для проверки. Неизвестное поле шаблона заполняйте
«неизвестно: <почему>», не догадкой. Назначение — отдельный assignment ID в control; без
control — «неизвестно», а число новых заданий клиента укажите отдельно. Если ни один вариант изменения не
выбран — одна строка «изменения не выбраны», без промпта.

## Ошибки и пограничные случаи

- **Нет memo и нет журнала расхода.** Разбор только по контексту parent; в первом вопросе
  прямо скажите, что данные неполные. Выводы о стоимости не делайте.
- **Нет механизма интерактивных вопросов.** Те же варианты нумерованным списком; ждите
  ответа номером. Не продолжайте без ответа.
- **Все находки класса `parent_deviation` или `task`.** Предложений по скилу нет: дайте
  пользователю короткие советы и не выдавайте промпт.
- **Пользователь просит сразу внести правку.** Этот скил правок не делает: выдайте промпт
  и скажите, что правку делает разработчик скила.
- **Сессия ещё идёт.** Разбирайте только завершённые назначения; активные child не
  трогайте и не прерывайте.

## Примеры

**Обычный случай.** Итог запуска: 6 child-сессий, каждая получила 16–35 новых заданий,
вход первого запроса до 241 тыс. токенов, все запущены с наследованием истории. Находки:
«наследование истории» (`client` + `skill`: умолчание клиента наследует беседу, правило
не требовало явного параметра), «переиспользование child на несколько назначений и ролей»
(`skill`: правило разрешало новую задачу в прежней сессии). Первый вопрос: «Найдено 2
проблемы, главная — 6 из 6 child унаследовали историю parent. Показать варианты?».

**Пограничный случай.** Один repair из-за неверного теста в брифе, расход не доступен.
Это не явный признак (нужно ≥2 repair): orchestrate разбор не предлагает. Если пользователь
сам попросил — находка `task`, советы без промпта.

**Отказ.** Пользователь выбрал «Нет» — ответ «Понял, разбор закрыт», ничего не записано.
