# Дизайн: orchestrate + Jev и выбор модели для любого клиента

Статус: реализовано (согласовано пользователем). Затрагивает публичный пакет `skills/orchestrate`.
Оценка по `dev`: T2 (новая возможность в нескольких файлах пакета, внешний сервис, секрет).

## 1. Цель

1. Тратить лимиты сильных моделей только там, где от них зависит качество, — для любого
   набора моделей любого клиента (Claude Code, DeepSeek Harness, Hermes, Codex и др.),
   без ограничения на число и состав моделей.
2. Отдать дешёвой модели-«решателю» Jev узкие суждения, которые сейчас делает
   дорогая модель координатора, — и сделать эти суждения проверяемыми и записанными.
3. Ничего не ухудшить без Jev: нет ключа, сети или Python — оркестратор работает как сейчас.

Не цели: Jev не пишет код, не принимает результат, не выбирает модель напрямую,
не видит исходный код и диффы. Свой установщик, MCP-сервер или SDK-зависимость не вводятся.

## 2. Что такое Jev и откуда берём доступ

- Jev — модель TypeSafe AI класса System One: отвечает на типизированные вопросы о
  переданном состоянии (`state`) и возвращает только данные с вероятностями:
  `choice` (выбор из вариантов + `probabilities`), `noul` (вероятность «да»),
  `score` (уровень по рубрике + `probabilities`). Текста не генерирует.
- Jev AI (jev-ai.pro) — сторонний провайдер, совместимый с API TypeSafe:
  `POST https://jev-ai.pro/api/v1/systemone`, `GET https://jev-ai.pro/api/v1/models`,
  `Authorization: Bearer $JEV_AI_API_KEY`, модель по умолчанию `jev-latest`.
- Формат запроса (по официальному SDK `@typesafe-ai/sdk` 0.7.0, `dist/index.d.mts`):
  `{state, questions: {<имя>: {type, instructions, criteria}}, model?}` →
  `{model, answers: {<имя>: ...}, usage: {input_tokens, output_tokens}}`.
  Ретраи SDK: 408, 429, 5xx. Контекст модели — 32k токенов.

## 3. Выбор способа интеграции

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| Официальный скил `typesafe-ai/skills` (`typesafe-ai`) | Лучшие практики от авторов модели | Учит **строить** интеграции; в рантайме ничего не вызывает | Использовать при разработке этой фичи (правила вопросов ниже взяты из него); в пакет не включать |
| MCP-серверы (`typesafe-mcp`, `@devbux/typesafe-mcp`, `codaaiteam/jev-mcp` и др.) | Готовые инструменты `jev_ask`/`jev_check` | Все сторонние; нужен Bun/Node; ключ в конфиге MCP хоста, не в `.env`; есть не во всех клиентах и не у child; каждый вызов идёт через контекст основной модели в свободной форме | Не использовать |
| SDK `@typesafe-ai/sdk` / `typesafe-sdk` | Официальный клиент, ретраи | Node 22+ или pip-установка в проекте потребителя — установка не является частью копирования скила | Не использовать в пакете |
| **Скрипт пакета на Python 3 stdlib, прямой HTTP** | Нет зависимостей; одинаково работает в любом клиенте с shell; ключ читает сам скрипт из `.env`, в контекст агента он не попадает; вопросы и таблица решений лежат в одном модуле и тестируются фикстурами | Свой код вызова (≈200 строк) | **Выбрано** |

## 4. Каталог моделей вместо списка Claude

Сейчас `runtime.model_map` сопоставляет три профиля с тремя моделями. Для произвольного
числа моделей вводим каталог и детерминированный выбор.

### 4.1 Каталог (в control запуска, `runtime.model_catalog`)

```yaml
model_catalog:
  client: <клиент>
  source: <откуда список: схема инструмента запуска / документация клиента>
  collected_at: <дата>
  models:
    - id: <фактический ID/алиас, как его принимает схема запуска>
      profile: light | coding | top   # класс качества, назначает parent
      cost_rank: 1                    # 1 — самая дешёвая; null — неизвестно
      context_tokens: <число | null>
      effort_values: [..] | null
      evidence: <ссылка/цитата, почему такой профиль>
```

Правила заполнения:
- Список берётся только из фактической схемы/документации клиента, ID по памяти не угадываются.
- `profile` назначает parent (не ниже `coding`) по описанию модели у клиента; не уверен — старший.
- Неизвестная стоимость (`cost_rank: null`) считается самой дорогой из профиля.
- Каталог переиспользуется при resume; меняется только при смене клиента или списка.

### 4.2 Выбор модели для назначения (детерминированный)

1. Порог назначения `floor` ∈ {light, coding, top} — по разделу 5 (правила + Jev).
2. Кандидаты: модели каталога с `profile ≥ floor` и подходящим контекстом.
3. Берётся минимальный `cost_rank`; при равенстве — младший профиль, затем первый по каталогу.
4. Кандидатов нет — `blocked: model_below_floor` (как сейчас, без тихого понижения).
5. Клиент не даёт выбирать модель child — `selection: unsupported`, как сейчас.

Так одинаково работают клиенты с одной моделью, с тремя или с сотней, а дешёвая модель
верхнего класса автоматически выигрывает у дорогой модели того же или младшего класса.

## 5. Где работает Jev

Принцип из официального руководства TypeSafe: **Jev даёт суждения, решения принимает код.**
Это совпадает с правилом 6 `model-selection.md` («дешёвая модель не принимает решений»):
решение принимает таблица в скрипте, а не Jev.

### 5.1 Калибровка назначения (основное место экономии)

Вызывается parent-ом перед каждым intent назначения (и при resume, если оценки нет).

`state` (только то, что parent и так пишет в brief; без кода, диффов и секретов):

```json
{
  "role": "worker",
  "goal": "...",
  "acceptance_criteria": ["..."],
  "planned_paths": ["src/..."],
  "review_md_risk": "low",
  "writes_code": true
}
```

`role`, `review_md_risk` и `writes_code` вычисляет parent/код по фактам, Jev их не угадывает.

Вопросы (одно суждение на вопрос; формулировки живут только в скрипте):

| Имя | Тип | Суждение |
|---|---|---|
| `size` | score 0–3 | T0 опечатка/константа · T1 локальная правка · T2 новая функция или несколько модулей · T3 новая система/сквозное изменение |
| `ambiguous` | noul | Требования допускают несколько разумных толкований |
| `design_choice` | noul | Нужно выбрать архитектурный вариант или границу |
| `security` | noul | Затрагивает аутентификацию, права, секреты или ввод извне |
| `migration` | noul | Меняет хранимые данные или их схему |
| `public_contract` | noul | Меняет публичный API/формат, от которого зависят другие |

Таблица решений (в коде; пороги noul — 0.7 «да», 0.3 «нет», между — «неясно»):

1. Жёсткий пол из фактов (Jev не может его понизить): `writes_code` → `coding`;
   `review_md_risk = high` → `top`; явное решение пользователя — как сейчас.
2. Любой из `security`/`migration`/`public_contract` = «да» → `top`.
3. Любой из них «неясно» → как «неизвестно» по правилу 4 → `top` для lead/verifier.
4. `P(size ∈ {T2,T3}) ≥ 0.3` или `ambiguous`/`design_choice` не «нет» → `top` для
   scout-решений/dev-lead/integrator; worker — `coding`.
5. Иначе: read-only роль без `design_choice` → `light`; остальное → `coding`.
6. Итог = max(пол, результат Jev). Verifier ≥ автора — как сейчас.

### 5.2 Причина неудачного repair

Перед эскалацией `coding → top` (сейчас parent решает сам, что причина — «качество рассуждения»).
`state` — отчёт child о неудаче и вывод проверок (обрезанный, без секретов).
Вопрос `cause` (choice): `brief_gap`, `environment`, `permissions`, `missing_data`,
`reasoning_error`; плюс noul `repeated_same_error`.
Код: эскалация на `top` только если `cause = reasoning_error` с p ≥ 0.7 и это второй
неудачный repair; `environment`/`permissions`/`missing_data` — блокер, не эскалация;
иначе решает parent по текущим правилам.

### 5.3 Где Jev не используется

Приёмка, вердикт verifier, слияние, Git-эффекты, разрешения, всё на путях security —
только по текущим правилам. Отказ или ошибка Jev — это ошибка, а не ответ «нет».

## 6. Режимы и порядок внедрения

`runtime.jev.mode` в control:

| Режим | Поведение |
|---|---|
| `off` | Нет ключа, Python или сети, либо пользователь выключил. Текущий порядок |
| `shadow` (по умолчанию при наличии ключа) | Parent калибрует как сейчас; Jev вызывается параллельно; оба результата пишутся в memo; применяется решение parent |
| `apply` | Применяется таблица раздела 5; parent может только поднять профиль с причиной |

Переход `shadow → apply` — по явному решению пользователя после отчёта о совпадениях
(сколько назначений, где Jev дал бы профиль ниже/выше и почему). Экономию называть только
по замерам клиента, как и сейчас.

## 7. Ключ, `.env` и данные

- Переменные: `JEV_AI_API_KEY` (обязательна для Jev), `JEV_AI_BASE_URL`
  (по умолчанию `https://jev-ai.pro/api`), `JEV_AI_MODEL` (по умолчанию `jev-latest`).
  Альтернатива — официальный провайдер: `TYPESAFE_API_KEY` → `https://api.typesafe.ai`.
- Порядок поиска: переменная окружения процесса → `.env` в корне **основного** checkout
  проекта. Корень находится через `git rev-parse --path-format=absolute --git-common-dir`,
  потому что `.env` в `.gitignore` и не попадает в worktree child-ов.
- Ключ читает только скрипт. Агент не открывает `.env` (правило «не читайте секреты»
  сохраняется), скрипт не печатает ключ, не пишет его в memo, логи и ошибки.
- Jev вызывает только parent; child-ам ключ не нужен и не передаётся.
- В Jev уходит только `state` из раздела 5 — текст brief без кода. Jev AI — сторонний
  посредник: перед первым вызовом в проекте parent одной строкой сообщает, какие данные
  уйдут и куда, и записывает согласие пользователя в memo.
- `.env` должен быть в `.gitignore` проекта; если нет — предупреждение, без правки.

## 8. Скрипт `skills/orchestrate/scripts/jev.py`

Python ≥ 3.9, только stdlib (`urllib`, `json`). Код выхода и JSON в stdout:

| Команда | Что делает |
|---|---|
| `jev.py config` | Найденная конфигурация без сети: провайдер, хост, модель, источник ключа (без значения) |
| `jev.py check` | Находит конфиг, `GET /v1/models` без инференса, печатает базовый URL, хост и доступные модели (без ключа). Это проверка «куда реально уходят запросы» |
| `jev.py calibrate --state FILE` | Строит вопросы раздела 5.1, вызывает Jev, применяет таблицу, печатает `{profile, rule, judgments, model, usage}` |
| `jev.py repair-cause --state FILE` | То же для 5.2: `{escalate: bool, cause, rule, ...}` |
| `--response-file FILE` | Для тестов: вместо сети читает сохранённый ответ |

Коды выхода: 0 — ответ; 2 — неверный вход; 3 — нет конфига/ключа (`mode: off`);
4 — сеть/таймаут/5xx после ретраев; 5 — 4xx API (ключ, баланс, лимит). Ретраи: 408, 429,
5xx, два повтора с паузой 1 и 3 с (или `Retry-After`); таймаут 10 с. Перед отправкой —
проверка размера `state` (с запасом под лимит 32k токенов).

## 10. Проверка

- Юнит: таблица решений на фикстурах (каждая строка 5.1/5.2, полоса «неясно»,
  пол не понижается), разбор ошибок 401/402/429/5xx, отсутствие ключа → код 3,
  ключ не появляется в stdout/stderr.
- Поведенческая (по CLAUDE.md): обычный запуск с ключом; пограничный — Jev отдаёт
  `size` между T1 и T2; без зависимости — нет `.env`/Python/сети → `mode: off`, текущий порядок.
- Живая: `jev.py check`, затем один `calibrate` на маленьком brief — на машине
  пользователя (из облачной сессии хосты jev-ai.pro и typesafe.ai закрыты сетью).
- `sh scripts/check-skills.sh`, `sh .claude/skills/dev/scripts/review-lint.sh`.

## 11. Риски

- Jev AI — посредник, не TypeSafe; документация сторонняя. Смягчение: `check` показывает
  реальный хост, базовый URL меняется одной переменной.
- Независимых замеров качества Jev нет. Смягчение: `shadow` по умолчанию, пол из фактов.
- Экономия может быть небольшой: основной выигрыш — каталог (4.2) и отказ от `top`
  там, где он не нужен; сам Jev экономит рассуждения parent о калибровке.
- Формулировки вопросов придётся подстраивать на реальных brief — только через фикстуры
  на новых случаях, без «подгонки» под отдельные примеры.
