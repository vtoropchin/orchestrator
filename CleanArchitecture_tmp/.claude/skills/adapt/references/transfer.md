# Манифест переноса и правила слияния

Что переносится в целевой проект, что не переносится никогда, и как класть файлы в проект, где
уже что-то есть.

## 1. Состав переноса

| Путь в источнике | Действие в цели | Примечание |
|---|---|---|
| `.claude/skills/<9 скилов дисциплины>/` | копировать целиком | `clean-architecture`, `solid-design`, `component-structure`, `architectural-boundaries`, `use-cases-and-entities`, `testable-architecture`, `code-organization`, `details-and-deferral`, `dev` |
| `.claude/skills/adapt/` | копировать целиком | чтобы набор можно было обновлять изнутри проекта |
| `.claude/skills/memo/`, `.claude/skills/memo-bootstrap/` | копировать + правка имени проекта (фаза 4) | только если `memo` подключается |
| `.claude/agents/` (7 файлов) | копировать целиком | |
| `.claude/settings.json` | **слияние JSON** | только хуки `memo`; чужие ключи не трогать |
| `.mcp.json` | **слияние JSON** | только сервер `memo` |
| `agentmemory.toml` | копировать + правка `[scope] project` | если файла в цели нет; иначе — не трогать |
| `.gitignore` | добавить строку `.env`, если её нет | не перезаписывать файл |
| `REVIEW.md` (в источнике нет — создаётся из `review-template.md`) | нет файла — создать каркас; есть — только дописать недостающее | **никогда не перезаписывать**: файл ведёт сессия репозитория |
| `.gitattributes` | дописать строку `REVIEW.md merge=union`, если её нет | не перезаписывать файл |
| `.claude/skills/dev/scripts/review-lint.sh` | копируется вместе с `dev` | после переноса — прогнать в корне цели (фаза 8) |
| `.env` | **никогда не копировать** | создать свой с пустым `DEEPSEEK_API_KEY=` |
| `README.md`, `ADAPTATION.md` набора | не копировать | только по явной просьбе, и тогда под именами, не конфликтующими с файлами проекта |
| PDF книги, `graphify-out/`, `.idea/`, `.git/` | не копировать | вес и мусор; конспект книги уже внутри `clean-architecture/references/book-digest.md` |

Копирование выполняется файлами набора как есть — без правок под язык (правило 2 в `SKILL.md`).

## 2. Первичная установка или обновление

Определяется до записи:

- **Первичная**: в цели нет `.claude/skills/clean-architecture/`. Переносится всё из таблицы.
- **Обновление**: набор уже стоит. Сравнить содержимое пофайлово и переносить только
  изменившиеся. **Не трогать**: `CLAUDE.md`, `agentmemory.toml`, `.env`, `settings.json`,
  `.mcp.json` — они уже адаптированы под цель. `REVIEW.md` — только дописать недостающее
  (`review-template.md`, «Обновление набора»), `.gitattributes` — строку
  `REVIEW.md merge=union`, если её нет. `memo`/`memo-bootstrap` при обновлении
  переносятся с повторной подстановкой имени цели, иначе вернётся имя источника.
- Файл набора, который в цели дополнен проектом (отличается и от прежней, и от новой версии
  источника), **сливается**, а не затирается — §2а. Чаще всего это `dev/SKILL.md`: проекты
  дописывают в него свои шаги, каналы отчёта и проверки.

## 2а. Слияние проектных дополнений в файлах набора

Для каждого файла набора, который в цели отличается от новой версии источника:

`memo`/`memo-bootstrap` сравниваются после подстановки имени цели в каждую версию источника —
иначе подстановка сама выглядит проектным дополнением.

1. **Найти прежнюю версию набора** (базу) — ту, с которой файл когда-то скопирован. Источник —
   git-репозиторий набора: перебрать версии файла `git -C <источник> log --format=%H -- <путь>`
   и для каждой сравнить `git -C <источник> show <коммит>:<путь>` с файлом цели.
   - Совпала байт-в-байт → проектных дополнений нет: файл просто заменяется новой версией.
   - Не совпала ни одна → база — версия с наименьшим diff к файлу цели (`diff | wc -l`);
     разница с ней и есть проектные дополнения.
2. **Показать дополнения**: `diff -u <база> <файл цели>` — это то, что проект дописал сам.
   Назвать их в плане фазы 2.
3. **Слить трёхсторонне** во временный файл в scratchpad:
   `git merge-file -p <файл цели> <база> <новая версия> > <scratchpad>/<имя>` — изменения
   набора ложатся поверх, дополнения проекта остаются.
4. **Без конфликтов** → итог проверить глазами (дополнения проекта на месте, изменения набора
   на месте) и записать в цель.
   **С конфликтами** (маркеры `<<<<<<<`) → разрешить по смыслу: правило набора берётся новым,
   проектное дополнение сохраняется рядом, переписанное под новую формулировку (например,
   ссылка на переименованную фазу). Неразрешимое — то есть дополнение противоречит новому
   правилу набора — конфликт: показать обе стороны и спросить по каналу из `CLAUDE.md`
   проекта; до ответа файл цели не трогать.
5. **Источник без истории** (не git, например `~/.claude/skills/`) → базы нет: показать
   `diff -u <файл цели> <новая версия>`, перенести проектные дополнения в новую версию
   вручную и показать итог в отчёте. Затирать дополнения нельзя и в этом случае.

После слияния в отчёте по каждому такому файлу — строка: «слит: N проектных дополнений
сохранено, конфликтов M (как разрешены)».

## 3. Слияние `.claude/settings.json`

Цель может иметь свои `hooks`, `permissions`, `env`. Порядок:

1. Прочитать существующий файл (если нет — создать из источника целиком).
2. Для каждого события (`SessionStart`, `UserPromptSubmit`) добавить хук `memo` в массив
   `hooks[<событие>]`, **не заменяя** существующие элементы.
3. **Идемпотентность**: если хук с подстрокой `memo` и тем же `-event` уже есть — пропустить.
4. Сохранить порядок и форматирование остальных ключей; перечитать и проверить валидность JSON.

Форма хука (путь к бинарю подставляется фактический, см. §5):

```json
{
  "matcher": "",
  "hooks": [
    {
      "type": "command",
      "command": "\"<путь-к-memo>\" hook -event session-start -config ${CLAUDE_PROJECT_DIR:-.}/agentmemory.toml"
    }
  ]
}
```

Для `UserPromptSubmit` — то же с `-event prompt-submit`. `${CLAUDE_PROJECT_DIR:-.}` оставлять как
есть: он раскрывается Claude Code в корень целевого проекта.

## 4. Слияние `.mcp.json`

1. Прочитать существующий; если нет — создать с одним сервером `memo`.
2. Добавить ключ `mcpServers.memo`, не трогая другие серверы.
3. Если `mcpServers.memo` уже есть — сравнить и спросить при расхождении, не перезаписывать.
4. `env.DEEPSEEK_API_KEY` оставить в форме `${DEEPSEEK_API_KEY:-}` — значение приходит из `.env`
   рядом с `agentmemory.toml`, memo подхватывает его сам при старте.

## 5. Бинарь `memo` и деградация

Путь в источнике абсолютный (`/Users/<...>/.local/bin/memo`) и на другой машине может не
существовать. Перед записью конфигов проверить `command -v memo`:

- бинарь найден → подставить фактический путь в оба конфига;
- не найден → **не подключать** ни хуки, ни MCP-сервер, не копировать `agentmemory.toml`, не
  переносить скилы `memo`/`memo-bootstrap`; записать в отчёт: набор работает без долговременной
  памяти, `dev` в этом случае проговаривает решения в отчёте вместо записи в память.

Частичная деградация (бинарь есть, ключа reasoner нет) допустима: recall работает на FTS5 без
суммаризации. Это не повод отказываться от переноса — только строка в отчёте.

## 6. Имя проекта в памяти

Фиксируется навсегда как scope в общей базе `~/.agentmemory/memory.db`. По умолчанию — имя
каталога цели; подтвердить у пользователя перед записью. Подставляется в:

- `agentmemory.toml` → `[scope] project`;
- `.claude/skills/memo/SKILL.md` — тело и `description` во frontmatter;
- `.claude/skills/memo-bootstrap/SKILL.md` — тело, заголовок и `description`.

После подстановки — проверить, что имя проекта-источника не встречается ни в одном файле цели.

## 7. Проверки после записи

1. Все скопированные каталоги совпадают с источником по составу файлов; слитые файлы (§2а)
   содержат и проектные дополнения, и изменения новой версии.
2. `REVIEW.md` есть, все разделы шаблона на месте; при обновлении прежнее содержимое файла
   не изменилось (`git diff REVIEW.md` показывает только дописанное); `review-lint` зелёный
   или его нарушения исправлены в этой же задаче.
3. Оба JSON-конфига валидны и содержат прежние ключи цели.
4. `.env` источника не скопирован; `.gitignore` цели содержит `.env`.
5. Старое имя проекта в цели не встречается.
6. Скилы и агенты видны сессии Claude Code в целевом проекте (после перезапуска сессии —
   назвать это пользователю как ручной шаг, если он работает в уже открытой сессии).
