# Набор скилов и агентов «Чистая архитектура»

Языко-независимый инструментарий для Claude Code, построенный по книге Роберта Мартина
*Clean Architecture: A Craftsman's Guide to Software Structure and Design*.

Оба издания лежат в этом каталоге. **Эталон — английский оригинал**
(`Clean Architecture A Craftsman Guide to Software Structure and Design.pdf`); русский перевод
(«Чистая архитектура. Искусство разработки программного обеспечения», Питер, 2018) используется
как вспомогательный: в нём есть места, искажающие смысл, — они помечены прямо в конспекте
`.claude/skills/clean-architecture/references/book-digest.md`.

Цель набора — та же, что у книги: **уменьшить человеческие трудозатраты на создание и
сопровождение системы**. Всё остальное (слои, порты, метрики) — средства, а не цель.

## Состав

### Скилы — `.claude/skills/`

| Скил | О чём | Когда срабатывает |
|---|---|---|
| **`adapt`** | **перенос набора в реальный проект и адаптация под его стек**: профилирование проекта → перенос со слиянием конфигов → имя проекта в памяти → блок правил в `CLAUDE.md` и каркас `REVIEW.md` → принуждение правила зависимостей → снятие ложных срабатываний; при обновлении `REVIEW.md` не перезаписывается, а проектные дополнения в скилах сливаются с новой версией | **разовая установка набора в проект и его последующие обновления (`/adapt update`)** |
| **`dev`** | **оркестратор цикла разработки**: калибровка уровня и риска задачи → понять → спроектировать → реализовать тестами изнутри наружу → проверить с доказательствами → ревью на баги → ревью архитектуры → закрыть; вызывает нужные скилы и агентов на гейтах; на модели Fable / Mythos сам пишет ТЗ и принимает работу, а код отдаёт агенту `implementer` на новейшем Opus | **любая задача «сделай/добавь/реализуй» — точка входа всего набора** |
| `clean-architecture` | ядро дисциплины: правило зависимостей, политика vs детали, уровни, круги | проектирование системы или функции, вопрос «куда положить код», ревью направления зависимостей |
| `solid-design` | SOLID на уровне модулей: SRP по акторам, OCP как иерархия защиты, LSP для любых подстановок, ISP, DIP | деление классов/модулей, дизайн интерфейсов, `if` по типу реализации |
| `component-structure` | REP/CCP/CRP, ADP/SDP/SAP, метрики I, A, D, главная последовательность | что класть в пакет/библиотеку, разрыв циклов, разделение монолита |
| `architectural-boundaries` | где и когда проводить границы, полные и неполные границы, формы пересечения, режимы разделения | «выделить ли это в сервис/модуль», абстракция «на будущее», рябь изменений |
| `use-cases-and-entities` | сущности, интеракторы, модели ввода/вывода, порты, презентаторы, кричащая архитектура | реализация фичи от требования, бизнес-логика утекла в контроллеры и SQL |
| `testable-architecture` | тесты как внешний круг, «Скромный объект», тестовый API, хрупкие тесты | медленные и ломкие тесты, вопрос «что мокать» |
| `code-organization` | упаковка по уровням/особенностям/портам/компонентам, видимость, принуждение компилятором | скелет проекта, именование каталогов, «архитектуру не видно в дереве» |
| `details-and-deferral` | БД, веб, UI, фреймворки, ОС и железо как детали; отложенные решения; `Main` | выбор технологии, фреймворк лезет в домен, старт проекта, встраиваемые системы |

Каждый скил содержит `SKILL.md` (процедуры, чек-листы, точки адаптации) и `references/`
(каталоги нарушений, метрики, шаблоны). Полный конспект книги —
`.claude/skills/clean-architecture/references/book-digest.md`.

### Агенты — `.claude/agents/`

| Агент | Задача | Продукт |
|---|---|---|
| `architecture-reviewer` | ревью кода/диффа против правила зависимостей, SOLID, компонентных принципов | ранжированные находки с минимальными исправлениями |
| `boundary-architect` | проектирование системы или крупной функции; оценка предлагаемого разделения | акторы, варианты использования, границы, порты, компоненты, `Main`, раздел «что НЕ делаем» |
| `use-case-designer` | требования → варианты использования, сущности, порты, модели I/O | слой бизнес-правил без UI и БД |
| `dependency-auditor` | аудит графа компонентов: циклы, SDP, I/A/D, зоны боли и бесполезности | отчёт с метриками и планом реструктуризации |
| `test-architect` | тестируемость как свойство архитектуры: швы, «Скромный объект», пирамида | диагноз, недостающие порты, план перевода тестов |
| `legacy-decoupler` | поэтапное распутывание легаси без переписывания | последовательность выпускаемых и проверяемых шагов |
| `implementer` | реализация одного шага фазы 3 по письменному ТЗ оркестратора (тест → код → рефакторинг); работает на новейшем Opus, зовётся только когда сессия идёт на Fable / Mythos | код, тесты и отчёт фактами: сделано, проверено, отклонения, вопросы |

### Внешние инструменты, на которые опирается цикл

| Инструмент | Роль в наборе | Где включён |
|---|---|---|
| `memo` (MCP + скил `memo`) | долговременная память проекта: recall в начале задачи, запись решений, компромиссов и границ вместо файлового журнала | фазы 1, 2, 5, 6 цикла `dev`; все агенты |
| `context7` (MCP) | актуальная документация библиотек, фреймворков, SDK, API, CLI | фаза 2 (выбор технологии) и фаза 3 (адаптеры) — **не при проектировании ядра** |
| `graphify` (скил) | устойчивый граф знаний по кодовой базе | фаза 1 на большой или незнакомой базе; при наличии `graphify-out/` вопрос о структуре проекта — сначала запрос к графу |
| `code-review`, `security-review` (встроенные скилы Claude Code) | ревью на баги в свежем контексте; уровень `code-review` задают уровень задачи и риск, `security-review` — при касании путей раздела «Безопасность» `REVIEW.md` | фаза 5а цикла `dev`, до архитектурного ревью |

Если инструмента в проекте нет — цикл выполняется без него: решения тогда проговариваются в
отчёте, документация берётся с осторожностью, ориентировка в коде идёт агентом `Explore`.

## Как использовать

Обычный путь — начать задачу с оркестратора, дальше он сам подтянет нужные скилы и агентов:

```
/dev добавь экспорт просроченных заказов для менеджера
```

Оркестратор калибрует уровень задачи (от однострочной правки до новой подсистемы) и риск
изменения (по путям из `REVIEW.md` проекта, а не по автору), проводит задачу через фазы и не
даёт перейти дальше, пока не выполнен гейт: сценарий сформулирован без UI и таблиц,
абстракции обоснованы, тесты ядра идут без инфраструктуры, прогон зелёный по факту запуска и
показан выводом, ревью на баги не оставило Important, блокирующих архитектурных нарушений
нет, отчёт содержит строки «Риск / Ревью / Откат» и то, что **не** сделано.

Ревью на баги устроено по подходу Anthropic: агент проверяет работу до человека, отдельным
ревью в свежем контексте (`/code-review` уровня по размеру и риску, `/security-review` по
путям), с отсевом шума (Important исправляется, Nit — списком, Pre-existing — задачей), не
больше двух кругов правок; находка, повторившаяся второй раз, становится автоматической
проверкой, а если это невозможно — правилом с glob-якорем в `REVIEW.md`. Встроенный
`/code-review` сам `REVIEW.md` не читает, поэтому `dev` сверяет diff с правилами отдельным
шагом. Гигиену файла (якоря, пути рисков, потолок 15 правил, сроки, дубли) проверяет скрипт
`.claude/skills/dev/scripts/review-lint.sh`; снятые правила уходят в архив памяти.
Детали фаз — `.claude/skills/dev/references/playbook.md`. Архитектурные решения (отложенные
технологии, сознательные компромиссы, проведённые границы) не ведутся в файлах проекта: они
хранятся в долговременной памяти `memo` — что и как формулировать, см.
`.claude/skills/dev/references/decisions-in-memo.md`.

Остальные скилы срабатывают автоматически по описанию задачи; агента вызывают явно:

```
Спроектируй структуру модуля отчётности — используй агента boundary-architect
```

```
Проверь мои изменения агентом architecture-reviewer
```

Скил можно вызвать напрямую: `/clean-architecture`, `/solid-design` и т. д.

## Как перенести в реальный проект

Обычный путь — скил `adapt`, из этого репозитория с указанием цели:

```
/adapt /путь/к/проекту
```

Он изучит проект, покажет план переноса, скопирует скилы и агентов, **сольёт** (а не перезапишет)
`.claude/settings.json` и `.mcp.json`, закрепит имя проекта в памяти, запишет стабильные правила
стека в `CLAUDE.md`, настроит автоматическую проверку правила зависимостей и снимет ложные
срабатывания, вызванные идиомами языка, создаст каркас `REVIEW.md` с путями риска. Этот
репозиторий при этом не изменяется. Если набор уже скопирован в проект — тот же скил
запускается там без аргумента (`/adapt`); обновить набор из этого репозитория —
`/adapt update /путь/к/этому/репозиторию` в проекте: `CLAUDE.md`, конфиги и `REVIEW.md`
сохраняются, проектные дополнения в скилах (например, в `dev/SKILL.md`) сливаются с новой
версией, а не затираются.

Ручной путь — то же самое по шагам:

1. Скопировать нужное в проект:
   ```bash
   cp -r ".claude/skills" ".claude/agents" /путь/к/проекту/.claude/
   ```
   или сделать доступным глобально — в `~/.claude/skills/` и `~/.claude/agents/`.
2. Пройти `ADAPTATION.md` и записать в `CLAUDE.md` проекта **стабильные правила** по
   языку/стеку (структура, видимость, команды проверки). Контекст, решения и история проекта
   в файлы не пишутся — они живут в `memo`.
3. Настроить автоматическую проверку правила зависимостей (архитектурный тест или линтер
   импортов) — без неё дисциплина держится только на ревью и не переживает дедлайн.
4. Завести `REVIEW.md` в корне проекта по шаблону
   `.claude/skills/adapt/references/review-template.md`, добавить в `.gitattributes` строку
   `REVIEW.md merge=union` и прогнать `sh .claude/skills/dev/scripts/review-lint.sh` — без
   `REVIEW.md` `dev` считает риск любого изменения средним.

## Принципы, на которых построен набор

- Правило зависимостей не подлежит нарушению; всё остальное — вопрос цены.
- Граница вводится в точке перегиба, а не «на всякий случай» и не «когда-нибудь потом».
- Детали (БД, веб, фреймворк, ОС, режим развёртывания) обязаны оставаться заменяемыми.
- Тестируемость — следствие границ, а не отдельная активность.
- Если система маленькая и стабильная, честный ответ агента — «дисциплина избыточна».

## Ограничения набора

Скилы и агенты не привязаны ни к одному языку: они не знают ваших идиом, инструментов сборки и
линтеров. Всё, что касается конкретного стека — модификаторы видимости, единицы сборки,
инструменты анализа импортов, механизм подмены в тестах — заполняется через `ADAPTATION.md`
в `CLAUDE.md` конкретного проекта.
